# IPTV TV Web App — Implementation Plan

## Goal
Build and deploy the IPTV streaming application described in `SPEC.md`:
- **TV Web App**: Next.js 16 (Turbopack) + TypeScript, targets Samsung Tizen / LG WebOS / Android TV
- **Backend API**: Node.js + Express + TypeScript, SQLite + Prisma, serves device activation, M3U, and Marvin API proxy
- **Shared**: Device activation with 6-digit code, channel grid with TV remote navigation, EPG timeline, native player integration with DRM fallback chain

---

## Where We Start

**SPEC.md** already defines:
- Architecture diagram
- Technology stack (Next.js + Express + Prisma/SQLite)
- Screen flow: Activation → Home/Channels → EPG → Player
- TV remote key mappings
- API endpoints (device, location, M3U, Marvin proxy)
- Database schema (Prisma)
- Platform-specific code (Tizen, WebOS, Android TV)
- Project structure

This plan assumes no existing code — we build from scratch at `/opt/data/tv-iptv/`.

---

## Approach

**Phase 1**: Scaffold both projects and verify they run

**Phase 3**: Build the frontend (activation → channel grid → EPG → player)

Each phase produces a working deliverable, not just files.

## Phase 2 — Backend API

### 2.1 Database setup
- `npx prisma generate` + `npx prisma db push` → creates SQLite dev.db
- Seed script: creates a default Location with a demo M3U URL, creates a Device with known activation code

### 2.2 Routes

**`POST /api/devices/register`** — Register new device, return 6-digit code
- Generate unique device ID from `uniqueId` field
- Generate random 6-digit code stored in `activationCode`
- Return `{ code, deviceId }`

**`POST /api/devices/activate`** — Activate with code
- Validate code + deviceId
- Set `isActivated = true`, set `activatedAt`
- Generate JWT token, store in `token` field
- Return `{ token, expiresAt }`

**`GET /api/devices/:id/status`** — Return device status and location

**`POST /api/devices/:id/deactivate`** — Clear activation

**Locations CRUD**: Full REST for `/api/locations`

**`GET /api/m3u/ip/:ip`** — IP-based M3U lookup
- Read `X-Forwarded-For` or socket remote address
- Match against location IP ranges
- Return `text/plain` M3U playlist (Content-Type: `application/vnd.apple.mpegurl`)

**`GET /api/m3u/code/:code`** — Code-based M3U lookup
- Return M3U for location matching this code

**`GET /api/m3u/device/:deviceId`** — Device-based M3U lookup

### 2.3 Marvin Service Proxy
- `POST /api/marvin/auth` → forward to Marvin, cache token
- `POST /api/marvin/auth/refresh` → forward refresh
- `GET /api/marvin/channels` → proxy channel list
- `POST /api/marvin/channels/detail` → proxy channel stream URL (key endpoint: returns `src`, `type`, `contentProtection`)
- `GET /api/marvin/epg` → proxy EPG data

### 2.4 Seed data
- Default location `DEMO` with a public M3U URL (e.g., a test playlist)
- One test device registered and activated

- Type: `TVAppConfig { apiBaseUrl, MarvinServiceUrl, appId, enableDRM, defaultCountry }`
- Store in React Context

### 3.3 Activation screen
- Shows device ID (formatted `XXXX-XXXX-XXXX`)
- On-screen numpad for 6-digit code entry (remote-optimized)
- States: idle → loading → error → success
- On success, store JWT in localStorage

### 3.4 Channel grid
- 4-column CSS grid (TV-optimized)
- Each card: channel logo + name + current program
- Remote navigation: Arrow keys move focus, Enter plays
- Focus state: orange highlight border + scale(1.05) + 200ms transition
- Category filter (All / Favorites / categories from API)
- Favorites stored in localStorage

### 3.5 EPG / TV Guide
- Horizontal timeline with channels as rows
- Current time indicator (vertical red line)
- Program blocks: title + start/end time
- Catch-up badge on past programs
- Navigation: Up/Down = channels, Left/Right = time (30-min steps)
- Press Enter on a program → play that channel

### 3.6 Player
- Player fallback chain: Native TV Player → video.js (hls.js/dash.js) → native HTML5 video
- Tizen: `tizen.tvplayer.play(url, { drm: ... })`
- WebOS: `webOS.player.play(url)`
- Android TV: `<video>` with EME (Encrypted Media Extensions) for Widevine
- Controls: play/pause (Space), seek (Left/Right), back (Backspace/Escape)
- Info banner: channel name, program title, progress bar

### 3.7 TV Remote hook
- `useTVRemote()`: listens for keydown on `window`, fires callbacks
- Key mapping from SPEC.md section 1.4
- Prevents default browser scroll on arrow keys

### 3.8 Styles
- `globals.css`: CSS variables for brand colors, TV-safe font sizes (min 16px body), focus ring
- `tv-optimized.css`: Focus states (highlight border, scale transform), grid layouts, scrollbar hiding ( TVs often have visible scrollbars otherwise)
- Font: Inter from Google Fonts
- All interactive elements: minimum 48x48px touch target (TV requirement)

## Key Risks & Decisions

### Risk 1: Marvin API credentials
SPEC says to integrate with `marvin.bcms-cdn.prod.aws.kpn.com` — credentials not provided yet. Backend route will be built to forward to whatever URL is configured in env. Placeholder auth will be implemented.

### Risk 2: Native player testing without hardware
The TV player integration (Tizen `tizen.tvplayer`, WebOS `webOS.player`) cannot be tested on a normal dev machine. Code will be written but untested until deployed to real hardware. Fallback chain (video.js → HTML5) can be verified in Chrome.

### Risk 3: CORS on TV devices
TV browsers have strict CORS. Backend will set `Access-Control-Allow-Origin` dynamically based on request origin, with `CORS_ORIGINS` env var as allowlist.

### Decision: SQLite vs PostgreSQL for backend
SPEC calls for SQLite — keeping it simple. On Coolify the DB file would be ephemeral, but the spec doesn't mention deployment target for this project. If they want to deploy to Coolify later, they can switch to PostgreSQL as they did with review-csv-studio.
